# PortGuard Mini v0.4 — read-only контроль VPS

Проект продолжает испытанную v0.3, **без Docker, сторонних Go-зависимостей и изменений сайта**. На VPS Go-компилятор не нужен: архив содержит готовый бинарник Linux amd64.

## Новое в 0.4

- Контроль изменений `/root/.ssh`, `/etc/ssh`, `sudoers`, cron и systemd unit-файлов, включая добавление, изменение и удаление файлов. Хранит только SHA-256, тип и права доступа, **не копирует содержимое SSH-ключей**.
- Проверка файлов и каталогов с защитой от следования по символическим ссылкам.
- Контроль наличия активного Fail2ban и таймера PortGuard.
- Отдельная выборочная проверка root-процессов, запущенных из `/tmp`, `/var/tmp`, `/dev/shm`, либо работающих из удалённого исполняемого файла.
- Команда `baseline-security` создаёт эталон безопасности **единственный раз**; не перезаписывает уже созданный эталон. На известной работающей VPS запускать после проверки файлов и служб.
- Поддержка существующего `baseline` портов, `audit`, `apply`, `rollback`, `watch` сохранена. **`watch` вызывает `apply`**; для автоматического наблюдения используется существующий `portguard-mini.timer`, который запускает только `audit`.

## Что не делает

Не блокирует сеть, не убивает процессы, не выключает VPS и не исправляет автоматически подозрительные файлы. Периодический опрос каждые 5 минут пропускает кратковременную активность, не может гарантировать обнаружение взлома root и может давать ложные тревоги при обновлениях системы. Эталон расположен **на самом VPS** и может быть изменён злоумышленником с root. Ошибки чтения отмечаются WARN, и не считаются свидетельством чистоты системы.

## Обновление на текущей VPS

Скачать `portguard-mini-v0.4.tar.gz` в `~/Downloads` на ПК. Из архива использовать только бинарник. Старые unit-файлы и `install.sh` повторно не запускать.

```bash
mkdir -p /tmp/portguard-v04
tar -xzf "$HOME/Downloads/portguard-mini-v0.4.tar.gz" -C /tmp/portguard-v04
scp /tmp/portguard-v04/portguard-mini/portguard root@203.0.113.10:/tmp/portguard-v04
ssh root@203.0.113.10 '
set -e
chmod 700 /tmp/portguard-v04
/tmp/portguard-v04 audit
cp -a /usr/local/sbin/portguard /root/portguard-previous
install -m 0755 /tmp/portguard-v04 /usr/local/sbin/portguard.next
mv -f /usr/local/sbin/portguard.next /usr/local/sbin/portguard
systemctl start portguard-mini.service
journalctl -u portguard-mini.service -n 55 --no-pager
'
```

После проверки доверенного состояния VPS отдельно выполнить **один раз**:

```bash
ssh root@203.0.113.10 '/usr/local/sbin/portguard baseline-security && /usr/local/sbin/portguard audit'
```

Сверить текущие файлы и настройки до принятия исходного состояния в качестве эталона. Новый мониторинг не следит за абсолютными значениями версий PHP/Go, только за их внешней выдачей по HTTP в текущих проверяемых ответах.

## Проверка исходников

Go 1.23+ на машине сборки: `go test ./...`, `go vet ./...`, `go build -o portguard .`. Исходники: `main.go`, `monitor.go`, `security.go` и соответствующие `_test.go`.

## Новое в v0.5 — события изменений в реальном времени

`watch-security` запускает inotify-наблюдение за каталогами из `securityTargets` (включая `/etc/ssh`, `/root/.ssh`, systemd и cron). Никаких дополнительных Go-библиотек нет. События создания, удаления, перемещения, закрытия после записи и смены атрибутов попадают в journal с `EVENT SECURITY`. Новые подкаталоги подключаются при обнаружении. Всякий раз, когда очередь событий переполнена, пишется `ALERT EVENT WATCH QUEUE OVERFLOW`.

**Это отдельный постоянно работающий процесс**, не замена периодического `audit`: после перезагрузки машины, при переполнении очереди, быстрой смене каталога и при полной компрометации root возможны пропуски. По содержимому файла срабатывает проверенная v0.4 (раз в 5 минут). Событие не доказывает взлома и не запускает блокировку или выключение.

### Обновление на существующем VPS

Установленный таймер и эталоны (`ports.json`, `security.json`) сохраняются. **Не запускать старый `install.sh` повторно**, не включать старый `watch`, поскольку он вызывает `apply`.

После скачивания `portguard-mini-v0.5.tar.gz` в `~/Downloads` на ПК:

```bash
mkdir -p /tmp/portguard-v05
tar -xzf "$HOME/Downloads/portguard-mini-v0.5.tar.gz" -C /tmp/portguard-v05
scp /tmp/portguard-v05/portguard-mini/portguard /tmp/portguard-v05/portguard-mini/install-event-watch.sh root@203.0.113.10:/tmp/
ssh root@203.0.113.10 'bash -s' <<'REMOTE'
set -eu
chmod 700 /tmp/portguard
/tmp/portguard audit
cp -a /usr/local/sbin/portguard /root/portguard-previous-v04
install -m 0755 /tmp/portguard /usr/local/sbin/portguard.next
mv /usr/local/sbin/portguard.next /usr/local/sbin/portguard
sh /tmp/install-event-watch.sh
systemctl start portguard-mini.service
systemctl status portguard-event.service --no-pager
systemctl list-timers portguard-mini.timer
REMOTE
```

Рекомендовано сначала проверить результат службы. Для безопасной проверки события можно использовать временный файл в `/etc/systemd/system` **без запуска** службы, как в ранее пройденном тесте. События смотреть через `journalctl -u portguard-event.service -n 30 --no-pager`.

### Ограничения

- inotify регистрирует изменение файла, но не знает, кто его изменил и было ли изменение вредоносным.
- События могут поступать пачками или повторяться, а короткоживущие каталоги могут быть пропущены при гонке.
- Это НЕ монитор всех путей, процессов, сетевых соединений и атак в реальном времени.
- Исходные эталоны внутри VPS может изменить взломщик с root.
- Если программа на VPS была заменена без перезапуска `portguard-event.service`, работающий процесс продолжает выполнять старый код; при обновлении версии нужно перезапустить службу.

## v0.6 — контроль собственной работоспособности и SSH-входов

Добавлен файл `selfguard.go` без внешних зависимостей. Команда `audit` теперь проверяет, что `portguard-event.service` и `portguard-mini.timer` активны и включены в автозагрузку, что у наблюдателя есть MainPID, а политика перезапуска соответствует `on-failure` или `always`. Выводит счётчик перезапусков, но **не выдаёт его за признак взлома**.

Также `audit` читает принятые SSH-входы за последние шесть минут через journald. Если доверенный список отсутствует, события обозначаются `SSH LOGIN OBSERVED`, без автоматического утверждения, что это взлом. При наличии `/etc/portguard-mini/trusted-ssh-ips` (по одному IPv4/IPv6 на строку, без подсетей и DNS) выводит `SSH LOGIN TRUSTED` либо `ALERT SSH LOGIN UNRECOGNIZED`. Правила IP пригодны для оповещения, но не доказывают принадлежность сессии атакующему: адрес администратора может измениться, а SSH-ключ может быть похищен. Список **не создаётся автоматически** и не нужен для запуска.

Команда не удаляет сессии, не изменяет ключи, сетевой доступ, процессы или учётные записи. При расследовании сначала установить личность и происхождение сессии, затем вручную отозвать скомпрометированные ключи, завершить подтверждённую постороннюю сессию и проверить систему с доверенной консоли. Если root скомпрометирован, все локальные проверки могут быть обойдены; надёжное восстановление требует переустановки VPS из проверенного образа и смены секретов **вне** этой машины.

### Обновление установленной v0.5 на VPS

Архив: `portguard-mini-v0.6.tar.gz` в `~/Downloads`. Текущие systemd units и эталоны оставляем без изменений. Не запускаем `install.sh` повторно.

```bash
mkdir -p /tmp/portguard-v06
tar -xzf "$HOME/Downloads/portguard-mini-v0.6.tar.gz" -C /tmp/portguard-v06
scp /tmp/portguard-v06/portguard-mini/portguard root@203.0.113.10:/tmp/portguard-v06
ssh root@203.0.113.10 'bash -s' <<'REMOTE'

install -m 0755 /tmp/portguard-v06 /usr/local/sbin/portguard.next

systemctl restart portguard-event.service
systemctl start portguard-mini.service
systemctl is-active portguard-event.service mini-site.service fail2ban.service
```

Перезапуск event-watch занимает небольшое время, в течение которого события inotify могут быть пропущены. Старый эталон `security.json` не сбрасывать: мы не добавили никаких новых unit-файлов. Режим `apply` и аварийное выключение не активированы.

## v0.7 — аварийная проверка (без автоматического выключения)

После проверки дерева проекта v0.6 добавлены команды:

- `portguard emergency-check` — только чтение: анализ успешных root-входов по SSH в журнале за последние 24 часа; **ничего не выключает и не блокирует**.
- `portguard emergency-off POWER_OFF` — **опасная ручная команда** для администратора, запрашивающая выключение VPS через systemd. Использовать только если есть доступ к консоли хостера и принято решение прекратить работу VPS. SSH-сессии завершатся при выключении. Данная команда не запускается таймерами или наблюдателем.

Доверенные отпечатки можно явно перечислить в `/etc/portguard-mini/trusted-root-key-fingerprints`: один `SHA256:...` на строку, комментарии с `#` допустимы. Это **не SSH-ключи**, а публичные отпечатки для сравнения с `sshd`-журналом. Если файла нет, выводится `UNCONFIGURED`, а незнакомые адреса не классифицируются как взлом. Не следует автоматически доверять всем отпечаткам из уже имеющихся журналов. Журнал может быть подменён скомпрометированным root или не содержать все события.

Установленная v0.6 продолжает аудит по таймеру и событийное наблюдение без изменений. Новый код не добавляет автоматический `poweroff`, смену ключей, завершение отдельных сессий или изменение firewall. Само наличие незнакомого root-ключа в SSH-журнале требует расследования и не гарантирует факта компрометации.

Обновление **без повторного запуска install.sh**: перенести готовый бинарник под временным именем, выполнить `emergency-check`, сохранить резервную копию `/usr/local/sbin/portguard`, атомарно заменить бинарник и перезапустить только `portguard-event.service`. Проверить журнал и `portguard-mini.timer`. Если на сервере локально менялись исходники, сравнить их до обновления.

## v0.8 — доверенный SSH-отпечаток и безопасная имитация инцидента

Проверена база v0.7. Добавлены команды `enroll-root-key SHA256:...` и `emergency-simulate`. Остальные рабочие функции оставлены без изменения.

- `enroll-root-key` создаёт `/etc/portguard-mini/trusted-root-key-fingerprints` **только если его ещё нет**, с правами 0600. Не изменяет `/root/.ssh/authorized_keys`, sshd или действующие сессии. Повторная запись запрещена. Регистрация не подтверждает, что сервер безопасен; перед вводом отпечатка нужно сверить его с локальным SSH-ключом.
- `emergency-check` проверяет SSH-журнал за последние 24 часа, сопоставляет отпечатки и выдаёт `TRUSTED KEY`, `ALERT UNKNOWN ROOT KEY` либо `ALERT UNVERIFIED ROOT LOGIN`.
- `emergency-simulate` печатает три фиктивных случая с адресами документационного диапазона 192.0.2.0/24: доверенный ключ, неизвестный ключ и вход без отпечатка. Ничего не меняет, не блокирует и не выключает VPS.
- `emergency-off POWER_OFF` остаётся **только ручным**. Никакого автоматического завершения SSH-сессий, смены ключей и отключения питания нет.

Внимание: SSH-журнал не является независимым доказательством проникновения. Вход с известным ключом не гарантирует подлинность пользователя; злоумышленник мог украсть ключ. Получение root через веб-приложение может пройти без SSH. Эти события нельзя автоматически привязывать к выключению VPS.

### Обновление уже работающего VPS

На ПК распаковать архив, передать **только бинарник** на VPS во временный путь, запустить `audit` и `emergency-simulate` после явной регистрации доверенного отпечатка. Сохранить старый бинарник, атомарно заменить `/usr/local/sbin/portguard`, перезапустить `portguard-event.service` и запустить `portguard-mini.service`. Не запускать `install.sh` повторно; не менять старые эталоны и systemd-units.
